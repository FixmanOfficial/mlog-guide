```
ulocate damaged core true @copper битыйX битыйY нашлось битый
```

На карте две двойные турели, и одна из них подбита: у неё `60` здоровья из `250`. Её поиск
и находит — целая соседка в счёт не идёт.

`damaged` смотрит только на **свои** здания: поля «метка» и «чужое ли» он не использует
вовсе. Ищет он ближайшее к юниту здание, у которого здоровье меньше предела.

Это ровно то, что нужно ремонтнику:

```
ubind @poly
ulocate damaged core true @copper x y нашлось цель
jump 0 equal нашлось 0
ucontrol approach x y 4 0 0
```

Поли подлетает к подбитому зданию, а чинит он его в игре сам: ремонт — его собственное
занятие, командовать им не надо. Программе остаётся только подвозить его к работе.

## «Нашлось» проверяют всегда

<Card kind="error">
**Когда поиск ничего не нашёл, старые координаты остаются на месте.** `ulocate` не обнуляет
их и не трогает вовсе — меняется только седьмое поле.

Программа, которая этого не проверяет, ведёт себя особенно неприятно: всё чинилось
и работало, последнее здание починилось — и юнит навсегда завис над тем местом, где
когда-то было повреждение.

Поэтому после каждого `ulocate` идёт проверка, и только потом команда.
</Card>

Это общее правило для всех четырёх видов поиска, а не особенность `damaged`.

## Ответ обновляется не каждую итерацию

`ulocate`, как и `uradar`, **пересчитывает находку раз в 40 тиков**, а в промежутке отдаёт
прошлый ответ. Причина простая: обойти всю карту дорого, а программа крутится по несколько
сотен раз в секунду.

Из этого следует пара привычек:

- не пытайтесь «обновить» поиск, повторив инструкцию подряд несколько раз: ответ будет
  один и тот же;
- не удивляйтесь, что починенное здание ещё две трети секунды числится подбитым.

<Card kind="note">
**`ulocate` берёт юнита под управление.** Это не просто вопрос: инструкция заводит юниту
контроллер и продлевает десятисекундный срок так же, как `ucontrol move`.

Значит, программа, которая только ищет и ничего не командует, всё равно держит юнита
при себе — он не вернётся к своим делам, пока она работает.
</Card>

## Четвёртый вид: `spawn`

У `ulocate` есть и четвёртый вид поиска — `spawn`, точка появления вражеских волн. Работает
он так же: координаты плюс «нашлось», здания там нет.

<Card kind="error">
В песочнице этого курса `spawn` не работает: волн и точек их появления в модели нет вовсе,
и пример на нём не построишь. В игре он на месте — ищет ближайшую точку высадки, ту самую,
вокруг которой ставят оборону.
</Card>

<Card kind="recap">
- `ulocate damaged` ищет ближайшее **своё** подбитое здание; метка и «чужое ли» ему не нужны.
- Не нашлось — координаты остаются прежними, меняется только поле «нашлось».
- Проверка находки обязательна для всех видов поиска.
- Ответ пересчитывается раз в 40 тиков.
- Поиск удерживает юнита под управлением, как обычная команда.
</Card>

<Card kind="task">
Поменяйте в примере первое поле с `damaged` на `building`, второе — с `core` на `turret`,
а третье с `true` на `false`: теперь ищется ближайшая своя турель, целая она или нет.
Найдётся та же самая — просто по другой причине: она ближе к юниту.

Потом оставьте `building turret`, но верните `true`: вражеских турелей на карте нет,
и `нашлось` станет нулём. Координаты при этом сохранят прошлый ответ — а если поиска
ещё не было, так и останутся пустыми: инструкция их просто не трогает.
</Card>
