Часть блоков в игре настраивают, ткнув в них и выбрав предмет: сортировщик, разгрузчик,
источник предметов, завод юнитов. То, что выбрано, и есть **настройка** блока — и логика
умеет её менять.

<Example client:load scene={CONFIG} world={true} />

Программа смотрит, чего на складе меньше, и настраивает сортировщик на этот предмет.
Меди 40, свинца 25 — значит сортировщик встанет на свинец.

## Только объектом и только тем, у кого настройка есть

```
control config sorter1 @lead
```

Третье поле — **объект контента**: `@lead`, `@titanium`, `@poly`. Не число и не строка.

<Card kind="error">
**Числом настройка не меняется.** `control config sorter1 3` выполнится и не сделает ничего:
игра проверяет, что значение — объект, и числовую ветку до настройки не доводит.

Отсюда типичная ловушка: предмет достали `lookup`-ом, положили в переменную — работает;
достали номер и забыли развернуть — строка молча бездействует.
</Card>

Настройка есть не у всякого блока. Логике подчиняются те, у кого она задаётся **контентом**:

| Блок | Чем настраивается |
| --- | --- |
| сортировщик, инвертированный сортировщик | предметом |
| разгрузчик, канальный разгрузчик | предметом |
| канальный и кинетический маршрутизаторы | предметом |
| источник предметов, источник жидкостей | предметом или жидкостью |
| наземная, воздушная и морская фабрики | типом юнита |
| конструкторы танков, кораблей и мехов | типом юнита |
| конструктор и большой конструктор | блоком |
| разгрузочный маршрутизатор, грузовой источник | блоком или типом юнита |

Всего таких блоков два десятка. Контейнер, бур и турель в список не входят: настраивать
у них нечего, и команда пройдёт мимо.

## Прочитать настройку — тем же `sensor`

```
sensor настройка sorter1 @config
```

Отвечает объект — тот же, что клали, — или пустота, если у блока настройки нет вовсе.
Сравнивать удобно прямо с константой: `jump 8 equal настройка @lead`.

<Card kind="note">
`@config` читается не у всех, кому его можно писать: игра отдаёт настройку только у блоков,
которые настраиваются контентом. У остальных — пустота, а не ноль.
</Card>

## Зачем это нужно

- **Один сортировщик вместо пяти.** Программа смотрит, чего не хватает, и перенастраивает
  его на ходу — линия сама везёт дефицитное.
- **Разгрузчик по требованию.** Ядро отдаёт именно то, чего просит фабрика.
- **Завод под задачу.** Одна фабрика делает то поли, то кинжала — смотря что нужно
  прямо сейчас.

<Card kind="error">
**Перенастройка стоит времени.** Блок, которому меняют настройку каждую итерацию, работает
хуже, чем настроенный один раз: конвейер перед сортировщиком успевает набиться не тем.
Настройку меняют по событию — «кончилось», «пришло», — а не каждую итерацию.
</Card>

<Card kind="recap">
- `control config блок @предмет` меняет настройку; значение должно быть объектом.
- Числом настройка не меняется, и предупреждения об этом не будет.
- Настраиваются логикой только блоки, у которых настройка — контент.
- Читается настройка через `sensor @config`, у остальных блоков там пустота.
</Card>

<Card kind="task">
Поменяйте в примере `@copper` и `@lead` местами и запустите: сортировщик встанет на медь —
условие осталось прежним, а значения поменялись.

Потом замените `control config sorter1 предмет` на `control config sorter1 3`. Настройка
не изменится вовсе: `@config` покажет прежний предмет, хотя строка выполняется каждую
итерацию.
</Card>
