Предмет можно назвать константой — `@copper`, `@graphite`. Но констант двадцать, и выписывать
их по одной в программу утомительно. У игры для этого есть **нумерованные списки**, и `lookup`
достаёт из них по номеру.

<Example client:load scene={TABLE} world={false} />

## Четыре списка

| Тип | Сколько в игре | Нулевой |
| --- | --- | --- |
| `item` | 20 | `@copper` |
| `liquid` | 11 | `@water` |
| `unit` | 56 | `@dagger` |
| `block` | 262 | `@graphite-press` |

```
lookup item предмет 0
```

Первое поле — какой список, второе — куда положить, третье — номер. За границей списка лежит
пустота, как и везде.

<Card kind="note">
Номера видит только логика. В интерфейсе игры их нет нигде, и порядок в списке — не порядок
исследования и не порядок в меню строительства: это внутренние номера контента, по которым
игра его сохраняет.
</Card>

## Сколько чего бывает

У каждого списка есть своя встроенная переменная с длиной:

```
set сколько @itemCount
```

`@itemCount`, `@liquidCount`, `@unitCount`, `@blockCount` — четыре числа, и ими же
заканчивают перебор. Вписывать `20` вместо `@itemCount` нельзя: в следующем обновлении
предметов станет больше, и программа перестанет видеть новые.

## Обратный перевод: `@id`

Номер по объекту спрашивают у самого объекта:

```
sensor номер @graphite @id
```

Отвечает `3` — графит третий в списке предметов. Обратно `lookup item обратно 3` вернёт тот же
графит. Это пригождается, когда предмет нужно **сохранить числом**: в ячейку памяти или во флаг
юнита объект не всякий раз положишь, а номер — обычное число.

<Card kind="error">
**Номера не вечны.** Они привязаны к версии игры: добавили новый предмет в середину списка —
и всё, что после него, съехало. Сохранённый в ячейке номер после обновления укажет на другой
предмет, и программа будет работать, просто не с тем.

Поэтому номером хранят **временно**, а в программе пишут константу: `@graphite` понятнее
и переживает обновления.
</Card>

## Зачем это на самом деле

<Example client:load scene={SCAN} world={true} />

Главное применение — **перебрать весь список**. Программа спрашивает склад про каждый предмет
по очереди и запоминает, какого больше всех: на табло появится `graphite: 60`.

```
lookup item предмет номер
sensor сколько container1 предмет
op add номер номер 1
jump 0 lessThan номер @itemCount
```

Без `lookup` пришлось бы выписать двадцать `sensor` подряд — и переписывать программу
после каждого обновления игры.

Тем же способом ищут, какого юнита на карте больше, чем занят завод, какой руды хватает
и какого блока в схеме нет.

<Card kind="recap">
- `lookup тип переменная номер` достаёт контент из нумерованного списка игры.
- Списков четыре: предметы, жидкости, юниты, блоки.
- Длина списка — во встроенной переменной: `@itemCount` и соседи.
- Обратно номер спрашивают у объекта: `sensor номер @graphite @id`.
- Номера привязаны к версии игры, поэтому в программе пишут константы.
</Card>

<Card kind="task">
Поменяйте во втором примере `item` на `liquid` в строке `lookup`, а `@itemCount`
на `@liquidCount`: программа начнёт искать самую полную жидкость. Контейнер жидкости
не держит, поэтому ответом будет первая же — `water: 0`.

Потом верните предметы и поставьте в `jump` число `3` вместо `@liquidCount`: перебор
остановится на первых трёх предметах, и графит с его шестьюдесятью в ответ уже не попадёт.
</Card>
