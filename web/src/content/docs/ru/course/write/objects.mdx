Место в памяти помнит не только значение, но и **вид** значения. Записали число — лежит
число; записали предмет — лежит предмет, а не его номер.

<Example client:load scene={OBJECTS} world={true} />

Программа кладёт в ячейку `@copper` и сам склад, достаёт их обратно и сразу пускает в дело:
прочитанный склад отвечает на `sensor`, прочитанный предмет годится ему в вопрос.

## Что можно положить

| Что | Пример |
| --- | --- |
| число | `write 120 cell1 0` |
| предмет, жидкость, блок, тип юнита | `write @copper cell1 0` |
| здание | `write container1 cell1 0` |
| юнит | `write @unit cell1 0` |
| строка | `write "готово" cell1 0` |
| пустоту | `write null cell1 0` |

Прочитанное годится везде, где годился бы оригинал: здание из ячейки можно спросить через
`sensor`, юниту из ячейки — отдать команду, предмет из ячейки — назвать в вопросе про запас.

<Card kind="note">
Раньше так было нельзя: в памяти жили только числа, и объект приходилось превращать в номер,
а на обратном конце разворачивать через `lookup`. Теперь это нужно только там, где номер
нужен сам по себе — перебрать весь контент по порядку, например.
</Card>

## Место помнит один вид за раз

Запись не «дописывает» вид к значению — она заменяет содержимое места целиком:

```
write @copper cell1 0
write 7 cell1 0
read что cell1 0
```

В `что` окажется `7`. Предмета там больше нет — не «предмет плюс число», а просто число.

Отсюда правило: **если в памяти лежит список разного, вид нужно знать заранее**. Программа
сама по прочитанному значению не поймёт, число это или юнит; проверить можно только косвенно,
строгим сравнением с `null` или попыткой спросить у него свойство.

## Юнит в памяти — ссылка, а не копия

Здание и юнит кладутся в память ссылкой на себя. Пока они живы, всё работает; когда погибают,
ссылка остаётся, а вот толку от неё нет.

<Card kind="error">
Юнит из ячейки нужно проверять перед тем, как им командовать:

```
read боец cell1 0
sensor мёртв боец @dead
```

Дальше командуют только тогда, когда `мёртв` равен нулю: переход с этим условием ставится
перед строками с командами.

После загрузки сохранения ссылка на погибшего юнита превращается в пустоту: юнит
записывается в сохранение номером, а на чтении по этому номеру уже никого нет. У зданий
так же — снесённый блок из памяти не воскресает.
</Card>

## Зачем это на практике

- **Очередь целей.** Нашли юнита радаром — положили в память; другой процессор взял оттуда
  и повёл.
- **Список складов.** Обошли связи через `getlink`, сложили в память те, что интересны,
  и дальше работают с готовым списком, а не перебирают всё заново каждый круг.
- **Один найденный блок на всех.** Дорогой поиск делается один раз, результат лежит
  в ячейке, и остальные процессоры просто читают.

Общая память двух процессоров — тема <Lesson lesson="write/shared">следующего урока</Lesson>.

<Card kind="recap">
- Память хранит значение вместе с видом: число числом, объект объектом.
- Прочитанный объект — полноценный: годится в `sensor`, в команды юнитам, в вопросы про запас.
- Новая запись затирает место целиком, вместе с прежним видом.
- Здания и юниты лежат ссылкой: погибший юнит остаётся ссылкой, а после загрузки сохранения
  становится пустотой.
</Card>

<Card kind="task">
Поменяйте в примере `write @copper cell1 0` на `write @lead cell1 0` и запустите: надпись
станет `lead: 0`. В ячейке лежит другой предмет, и спрошено про него же — свинца на складе нет.

Потом верните медь и поменяйте `write container1 cell1 1` на `write @this cell1 1`: теперь
в памяти лежит сам процессор, и `sensor` спросит про медь у него. Надпись станет `copper: null` —
не ноль, а пустота: склада у процессора нет вовсе, и вопрос к нему неприменим.
</Card>
